# 테스트 코드 작성을 위한 규칙입니다 

테스트 코드 작성에서 LLM이 지켜야 할 규칙입니다. 

# 0. 가장 중요한건 생산성 원칙입니다  

테스트 코드의 작성 의도 아래와 같습니다  

- 내가 생각하는 대로 잘 동작하는가?
- 내가 생각한 예외 상황을 잘 커버하는가? 
- 다른 코드가 변경 되었을 때, 이 코드가 잘 동작하는지 아니면 깨지는지를 잘 보여줄 수 있는가? 
- 테스트 코드를 작성해둠으로써, 향후 코드 변경이나 리팩토링 과정에서 걱정 없이 코드를 작성하고 테스트 결과를 신뢰하여 문제없는 동작을 보장할 수 있는가?

테스트 코드 작성은 당장의 버그 발견과 동작 검증도 있습니다. 하지만 더 나아가서 테스트 코드는 생산성 향상과 사이드 이펙트 발견 및 코드 품질에 기여를 합니다. 
예를 들어 향후에 이뤄질 코드 변경 이후에 테스트를 통해서 문제나 변경 포인트를 조기에 발견하여 QA 비용 및 사용자 레벨에서 발견되는 버그를 줄이고 예방할 수 있습니다. 
  
# 1. 구현 코드는 Testable Code로 작성 

항상 구현 코드는 Testable 해야합니다. 필요에 따라 순수 함수 형태로 추려내서 로직을 testable하게 만들어야 합니다. 
예를 들어 복잡한 코드가 있고 500줄 이상이며 개념적으론 요청 하나를 처리하지만 커버해야 하는 구현 디테일과 예외 케이스가 매우 넓은 경우가 있습니다.  
이 경우 testable을 위해서 하나의 단일 거대한 서비스 로직은 예외 케이스 검사나 로직 흐름을 분리하고, 복잡한 하나의 로직은 나뉘어진 세부 구현 코드로 구성해야 합니다.  

# 2. 하나의 테스트 메서드는 하나의 관심사를 검증해야 합니다  

테스트 하나는 해당 구현체가 담은 개념에서 계층적으로 볼 때 동일한 계층 하나만 검증해야 합니다. 
원하는 조건이나 상황을 테스트 하고 싶지만 다른 조건이 너무 많이 가정이 되어야 한다면, 해당 구현 코드가 여러 관심사를 커버하고 있는건 아닌지 체크해야 합니다.  
구현 코드와 도메인 설계 과정에서 관심사를 잘 정의하고 계층 구조로 분리해야 테스트 메서드 작성에서 하나의 관심사씩 테스트 할 수 있습니다.  
다만 복잡한 연관관계가 얽힌 상황과 이를 필연적으로 다뤄야 하는 레이어에서는 여러 관심사나 사전에 작업되어야 할 상황 가정이 복잡하고 하나에 테스트에서 여러 관심사를 커버해야 할 수도 있습니다. 

# 3. 테스트 메서드 이름은 해당 테스트를 간결하게 설명할 수 있어야 합니다 

테스트 메서드 이름은 구현 코드와 달리 서술식으로 작성합니다. 테스트 메서드 이름은 영어로 구성하고 `@DisplayName` 어노테이션을 통해서 한국어로 설명합니다. 
테스트 메서드 이름은 테스트 디버깅 과정에서 빠르게 확인하고 판단할 수 있어야 하므로, 간결하면서도 해당 테스트가 어떤 부분을 테스트하는지 잘 설명할 수 있어야 합니다.

# 4. 유닛 테스트가 지나치게 복잡하다면, 이는 통합 테스트가 필요하거나 구현을 개선해야 할 수 있습니다 

지나치게 복잡해진 유닛 테스트는 mocked 상황이 실제 라이브 상황과 유사하지 못할 수 있습니다. 
유닛 테스트가 어렵도록 코드가 구성이 되었다면 해당 구현 코드가 testable code를 벗어났는지 점검하고, 필연적으로 복잡해질 수 밖에 없는 코드인지 아니면 구현을 개선해야 할지 재판단 해야 합니다.
